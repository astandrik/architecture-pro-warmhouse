### 1. Описание функциональности монолитного приложения

**Управление датчиками:**

- Пользователи могут создавать, просматривать, обновлять и удалять датчики температуры через REST API
- Система поддерживает базовые CRUD операции над конфигурацией датчиков
- Функционал включения/выключения физического отопления НЕ реализован в коде (только описан в бизнес-требованиях)
- **_Система предоставляет доступ ко всем датчикам в системе без разграничения прав доступа_**!

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в разных помещениях
- Система получает данные температуры в режиме реального времени от внешнего temperature-api
- Доступны два способа запроса: по названию помещения (без sensor ID) или по ID датчика
- Система хранит только последнее значение с отметкой времени
- **_Отсутствует механизм аутентификации и разделения данных между пользователями_**!

**Подключение датчиков к системе:**

- REST API позволяет создавать датчики через POST /api/v1/sensors без проверки прав
- Подключение нового дома и устройств выполняет только специалист компании.
- Специалист выезжает на объект, устанавливает датчики и реле, настраивает их подключение к системе.
- Отсутствует аутентификация: любой клиент может вызвать CREATE/UPDATE/DELETE операции

### 2. Анализ архитектуры монолитного приложения

**Технологический стек:**

- Язык программирования: Go
- Web-фреймворк: Gin
- База данных: PostgreSQL

**Архитектурная организация:**

- Паттерн: трёхслойная архитектура
  - handlers — обработка запросов, валидация, формирование ответов
  - services — интеграция с внешним апи температуры
  - db — SQL-запросы

**Характеристики взаимодействия:**

- Блокирующие HTTP-вызовы к внешнему temperature-api
- Сервер опрашивает API только для датчиков типа Temperature при каждом запросе GET /sensors
- Прямые HTTP GET запросы с таймаутом 10 секунд

**Развёртывание:**

- Контейнеризация: multi-stage Dockerfile
- Конфигурация - через переменные окружения
- Хэлсчеки: GET /health

### 3. Определение доменов и границы контекстов

**Текущая система:**

**Домены**

**Домен «Управление Устройствами»**

- Регистрация и учёт устройств (датчики температуры, реле отопления, в будущем — свет, камеры, ворота и другие модули).
- Привязка устройств к конкретному дому и пользователю.
- Управление состоянием устройств(реле) (включить/выключить, открыть/закрыть и т.п.).

**Домен «Телеметрия»**

- Получение данных от датчиков.
- Хранение и предоставление телеметрии пользователю.

**Текущие контексты в монолите**

**Контекст 1: Управление Датчиками**

- Регистрация и конфигурация только температурных датчиков через REST API
- CRUD операции без привязки к пользователю или дому
- Хранение метаданных в таблице sensors (id, name, type, location, unit)
- Датчики здесь как источник источник данных о датчике

**Контекст 2: Сбор Телеметрии**

- Получение актуальных показаний температуры от внешнего temperature-api
- Обновление текущего значения датчика (без сохранения истории)
- Датчики здесь как источник телеметрии

Почему контексты смешаны:

Например вот тут в функции
// GetSensors handles GET /api/v1/sensors
func (h *SensorHandler) GetSensors(c *gin.Context)

В запросах к сенсорам (текущим данным температуры) нет никакой необходимости каждый раз перезапрашивать
данные о датчиках пользователя - датчики пользователя меняются либо при установке специалистом либо при ошибке (отключили от сети)
что происходит явно реже чем изменение температуры.

### **4. Проблемы монолитного решения**

**Проблемы масштабируемости:**

- Невозможность независимого масштабирования компонентов (все масштабируется вместе)
- Единственная точка входа обрабатывает все типы запросов
- Рост нагрузки на телеметрию влияет на производительность CRUD операций с датчиками (из-за смешанных контекстов)

**Проблемы развёртывания и поддержки:**

- Обновление любого компонента требует перезапуска всего приложения
- Отсутствие возможности постепенного развёртывания
- Ошибка в одном модуле приводит к отказу всей системы

**Проблемы производительности:**

- Синхронные блокирующие вызовы к temperature-api замедляют обработку запросов
- Отсутствие кэширования температурных данных
- Каждый запрос GET /sensors вызывает множественные обращения к внешнему API

**Проблемы расширяемости:**

- Система поддерживает только температурные датчики
- Добавление новых типов устройств (освещение, ворота, камеры) требует модификации монолита
- Отсутствует архитектура для подключения устройств партнёров по стандартным протоколам
- Невозможность самостоятельного подключения устройств пользователями

**Проблемы безопасности:**

- **_Полное отсутствие аутентификации и авторизации!_**
- Все пользователи имеют доступ ко всем датчикам в системе

**Проблемы надёжности:**

- Нет изоляции ошибок - проблема в одном компоненте влияет на всю систему
- Нет механизма retry при сбоях внешнего API
- Невозможность независимого восстановления отдельных компонентов

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов используются оба подхода:

- **REST API (OpenAPI)** — для синхронных запросов, когда сервису нужен немедленный ответ (создание команд устройств, получение структуры домов, запрос данных об устройстве, приём телеметрии по HTTP).
- **AsyncAPI** — для асинхронной передачи телеметрии от устройств и шлюзов через брокер сообщений, когда отправителю не нужен немедленный ответ.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1. сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2. Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3. Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

# **Задание 6. Разработка MVP**

Необходимо создать новые микросервисы и обеспечить их интеграции с существующим монолитом для плавного перехода к микросервисной архитектуре.

### **Что нужно сделать**

1. Создайте новые микросервисы для управления телеметрией и устройствами (с простейшей логикой), которые будут интегрированы с существующим монолитным приложением. Каждый микросервис на своем ООП языке.
2. Обеспечьте взаимодействие между микросервисами и монолитом (при желании с помощью брокера сообщений), чтобы постепенно перенести функциональность из монолита в микросервисы.

В результате у вас должны быть созданы Dockerfiles и docker-compose для запуска микросервисов.

В данном репозитории реализовано минимальное MVP:

- `apps/telemetry-svc` (Node.js/TypeScript):
  - `POST /v1/telemetry` — приём телеметрии
  - `GET /v1/telemetry?device_id=&limit=` — запрос последних записей
- `apps/device-mgmt-svc` (Node.js/TypeScript):
  - `POST /v1/device-commands` — создать команду устройству
  - `GET /v1/device-commands/{id}` — статус команды
- Монолит (Go) проксирует:
  - `POST /api/v1/device-commands` → device-mgmt
  - `GET /api/v1/telemetry` → telemetry

UI дашборд доступен по адресу http://localhost:8080/ui/ и отображает сенсоры с данными, получаемыми от `temperature-api`.

### Запуск стека и UI

```bash
cd apps
docker compose up -d --build
```

- Монолит (API): http://localhost:8080
- UI дашборд: http://localhost:8080/ui/
- Temperature API: http://localhost:8081/temperature?location=Living%20Room
- Telemetry Service: http://localhost:8091/health
- Device Mgmt Service: http://localhost:8092/health

Postman коллекция: `apps/smarthome-api.postman_collection.json`

Остановка:

```bash
cd apps
docker compose down
```
